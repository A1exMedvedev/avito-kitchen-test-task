# Кухня — MVP сервиса доставки еды

API для веб-клиента и закрытое API для заведений, подключённых к площадке.

Репозиторий содержит два сервиса, которые поднимаются вместе:

| Сервис | Что делает | Порты |
|---|---|---|
| **kitchen** | Платформа: REST для покупателя, gRPC для заведений, доставка событий | `8080` REST, `9090` gRPC |
| **partner-demo** | Пример заведения — отдельный сервис, интегрированный через публичное API платформы | `8081` |

---

## Запуск

Нужен только Docker. Ни Go, ни генераторов на машине не требуется —
кодогенерация происходит внутри сборки образа.

```bash
task up
```

Или напрямую, без Task:

```bash
docker compose up -d --build
```

Первая сборка занимает около полутора минут. Миграции и демо-данные
накатываются автоматически при старте.

После запуска:

| Что | Адрес |
|---|---|
| **Swagger UI** | <http://localhost:8088> |
| REST API | <http://localhost:8080/api/v1> |
| OpenAPI-схема | <http://localhost:8080/openapi.json> |
| gRPC (с рефлексией) | `localhost:9090` |
| Экран кухни заведения | <http://localhost:8081/kds> |
| PostgreSQL | `localhost:5433`, `kitchen` / `kitchen` |

Остановить:

```bash
task stop      # остановить, данные сохранить
task down      # остановить и удалить базу
```

## Демонстрация

```bash
task demo
```

Скрипт проходит 13 сценариев по живому стенду и печатает результат каждого.
Занимает около минуты — большая часть уходит на ожидание, пока сервис заведения
проведёт заказ через все стадии.

Что проверяется:

| # | Сценарий |
|---|---|
| 0 | Платформа поднялась и отвечает |
| 1 | Витрина: закрытые заведения остаются в списке, а не исчезают |
| 2 | Меню с живыми остатками и доступностью каждого блюда |
| 3 | Наполнение корзины, пересчёт итога и готовности к оформлению |
| 4 | Попытка добавить блюдо из другого заведения — отказ сразу, а не на оплате |
| 5 | Оформление: заказ, списание остатка и уведомление кухне одной транзакцией |
| 6 | Повтор запроса после обрыва сети возвращает тот же заказ, а не создаёт второй |
| 7 | Сервис заведения получает заказ по gRPC и ведёт его до доставки |
| 8 | Распроданное блюдо и блюдо, выключенное кухней, — разные причины отказа |
| 9 | Закрытое заведение |
| 10 | Отмена заказа возвращает порции в меню |
| 11 | Заведение пытается достать чужой заказ — не находит |
| 12 | Собственный экран кухни примера заведения |

В конце — `All scenarios passed.`

### Потыкать руками

Откройте <http://localhost:8088>, нажмите **Authorize**:

| Поле | Что вписать |
|---|---|
| `customerAuth` | любой UUID, например `11111111-2222-4333-8444-555555555555` |
| `partnerAuth` | ключ заведения, см. ниже |

Покупатель создаётся при первом обращении — регистрации нет, авторизация вне
рамок MVP.

Три засеянных заведения:

| Заведение | Ключ | Особенность |
|---|---|---|
| Хинкальная №1 | `demo-hinkalnaya-6f3a1c9d4b2e8a70` | **управляется роботом** `partner-demo` |
| Pizza Avenue | `demo-pizza-4c81e2b7a95d0f36` | ручное управление, есть распроданные блюда |
| Sushi Lab | `demo-sushi-2a7d9e13c4b60f85` | закрыто |

Хинкальную ведёт сервис-робот: оформите туда заказ и обновляйте
`GET /orders/{id}` — статусы поедут сами. Чтобы жать кнопки самому, берите
**Pizza Avenue**, там робота нет.

Идентификаторы блюд генерируются при создании базы — берите их из
`GET /venues/{venueId}/menu`, а не из документации.

## Работа через Task

Сборка, тесты и кодогенерация — через [Task](https://taskfile.dev).
`task --list` покажет всё с описаниями.

```bash
task tools     # один раз: поставить закреплённые генераторы и линтеры
```

Нужно только для локальной работы с Go. Для `task up` не требуется.

**Повседневное:**

| Команда | Что делает |
|---|---|
| `task up` | Поднять всё: базу, платформу, заведение, Swagger UI |
| `task demo` | Прогнать все бизнес-сценарии |
| `task logs` | Логи платформы и заведения |
| `task ps` | Состояние контейнеров |
| `task psql` | Консоль psql в работающей базе |
| `task down` | Остановить и удалить данные |

**Разработка:**

| Команда | Что делает |
|---|---|
| `task check` | Формат, линтеры и тесты — то же, что гоняет CI |
| `task test` | Юнит-тесты с детектором гонок |
| `task test:integration` | Тесты против настоящего PostgreSQL |
| `task cover` | Отчёт о покрытии в `coverage.html` |
| `task lint` | golangci-lint и линтер proto-контракта |
| `task generate` | Перегенерировать всё в `api/gen` |
| `task proto:breaking` | Проверить контракт на обратную совместимость |
| `task diagrams` | Перерисовать PlantUML-диаграммы в PNG |

Сгенерированный код в репозиторий не коммитится. Задачи, компилирующие Go,
зависят от генерации, поэтому `task test` на чистой машине сначала сам
сгенерирует код из контрактов.

**Порядок, который важно помнить:** `go mod tidy` и форматирование импортов —
только **после** `task generate`. Без `api/gen` первое выкинет зависимости
из `go.mod`, второе — импорты из файлов.

## Настройки

Всё работает без настройки. Если нужно поменять — скопируйте шаблон:

```bash
cp .env.example .env
```

Чаще всего меняют `POSTGRES_PORT` (если 5433 занят), `LOG_LEVEL`
и задержки робота-заведения `PARTNER_*_DELAY`.

Политику примера заведения можно менять на лету, без перезапуска:

```bash
# выключить автопилот — заказы будут ждать решения человека
curl -X PUT http://localhost:8081/kds/policy \
  -H 'Content-Type: application/json' -d '{"auto_accept": false}'
```
